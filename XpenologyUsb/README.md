# Xpenology USB Writer

Xpenology(헤놀로지)를 베어메탈로 설치할 때 쓰는 부팅 USB를 만드는 프로그램입니다.

로더를 직접 찾아 받고, 압축을 풀고, Rufus로 굽는 과정을 하나로 합쳤습니다.

## 받기

[Releases](https://github.com/svrforum/SFTool/releases)에서 `XpenologyUsb-portable.exe`
하나만 받으면 됩니다. 설치가 필요 없습니다.

실행이 안 되면 `-setup.exe` 쪽을 받으세요. 이 프로그램은 윈도우에 들어 있는
WebView2를 씁니다. Windows 11에는 기본으로 있고 Windows 10에도 대부분 있지만,
업데이트를 오래 막아둔 기계에는 없을 수 있습니다. `-setup.exe`는 그것까지 같이
설치합니다.

서명되지 않은 프로그램이라 SmartScreen 경고가 뜹니다. "추가 정보" → "실행"으로
진행하시면 됩니다. 받은 파일이 여기서 빌드된 것과 같은지는 릴리스 페이지의
SHA-256으로 확인하실 수 있습니다.

**백신이 파일을 지울 수도 있습니다.** USB에 부트로더를 굽는 일은 디스크의 첫
섹터를 덮어쓰는 것이고, 그 동작은 백신 입장에서 부트킷과 구분되지 않습니다.
여기에 코드 서명까지 없으면 Windows Defender 가 차단하는 경우가 있습니다.
이 프로그램은 시스템에 아무것도 남기지 않습니다 — 레지스트리도, 서비스도,
시작 프로그램도 만들지 않고, 선택한 USB 밖으로는 파일을 쓰지 않습니다.
자세한 내용과 대응은 [`docs/DEFENDER_FALSE_POSITIVE.md`](docs/DEFENDER_FALSE_POSITIVE.md)
에 있습니다.

## 쓰는 법

1. `.exe`를 실행합니다 (관리자 권한 창이 뜨면 허용해 주세요)
2. USB를 고르고, 로더를 고르고, 확인합니다
3. 완료되면 안전 제거를 누르고, 그 USB로 부팅합니다
4. 로더 화면에서 시놀로지 모델·시리얼·MAC을 설정합니다

**모델 선택은 이 프로그램이 하지 않습니다.** m-shell과 RR의 이미지는 모델 정보가
없는 범용 raw 이미지입니다. 이 프로그램의 책임은 "올바른 이미지를 올바른 USB에
정확히 굽는 것"에서 끝납니다.

알아두실 것:

- 선택한 USB의 데이터는 전부 지워집니다
- 8GB 이상 USB가 필요합니다
- 쓰기가 끝나면 윈도우가 "디스크를 포맷하세요"라고 물어볼 수 있습니다.
  **정상이며 취소를 누르세요.** 리눅스 파티션이라 윈도우가 읽지 못할 뿐입니다

## 어떻게 굽는가

Rufus의 DD 모드와 같은 방식입니다. 이미지를 변형하지 않고 **섹터 단위로 그대로**
씁니다. 섹터 크기는 512로 가정하지 않고 장치가 보고하는 값을 씁니다.

순서는 이렇습니다.

1. **확인** — GitHub에서 최신 릴리스를 찾고 에셋을 고릅니다
2. **내려받기** — 발행자가 `sha256sum`을 함께 올렸으면 대조합니다.
   어긋나면 **장치를 열기 전에** 멈춥니다
3. **압축 해제** — 임시 파일로 떨구지 않고 장치로 바로 흘려보냅니다.
   3GB짜리 여유 공간이 없는 기계에서도 동작합니다
4. **준비** — 드라이브 문자를 떼고, 파티션 테이블을 지우고, 장치를 잠급니다
5. **쓰기** — 8MiB씩 raw로 씁니다. **맨 앞 1MiB는 보류했다가 맨 마지막에 씁니다**
6. **검증**(선택, 기본 꺼짐) — 쓴 내용을 되읽어 SHA-256으로 대조합니다
7. **마무리** — 장치 끝의 1MiB를 0으로 덮습니다

5번의 보류가 필요한 이유가 있습니다. 이미지의 첫 부분에는 그 이미지 자신의 파티션
테이블이 들어 있습니다. 그걸 오프셋 0에 쓰는 순간 장치에 유효한 파티션 테이블이
생기고, 윈도우가 **쓰는 도중에** 볼륨을 마운트합니다. 새로 생긴 볼륨은 잠겨 있지
않으므로 그 섹터에 닿는 순간 쓰기가 거부됩니다. 실제로 24MiB 지점에서 그렇게
실패했습니다. 그래서 나머지를 다 쓴 뒤에 앞부분을 채웁니다.

7번은 이미지가 USB보다 작을 때 끝에 남은 옛 GPT 백업 헤더 때문입니다. 그대로 두면
윈도우가 방금 지운 파티션 테이블을 되살립니다.

### 검증 (선택)

**기본으로 꺼져 있습니다.** 확인 화면의 체크박스로 켤 수 있습니다.

켜면 쓰면서 쌓아 둔 SHA-256과 되읽은 내용을 대조합니다. 쓰기가 끝났다는 말은
장치가 오류를 돌려주지 않았다는 뜻일 뿐이고, 불량 USB는 조용히 다른 바이트를
돌려줍니다. 그건 부팅이 안 되는 시점에야 드러나고, 그때는 원인이 USB인지
로더인지 알 수 없습니다. 검증은 그 구분을 굽는 자리에서 끝냅니다.

**그런데 기본으로 켜 둘 수가 없습니다.** 검증이 의미를 가지려면 파티션 테이블을
쓰기 **전에** 되읽어야 합니다. 테이블이 놓이는 순간 윈도우가 첫 파티션을
마운트하고 FAT 메타데이터를 써 넣어서, 멀쩡한 USB가 불량으로 보고되기 때문입니다.
그런데 그 순서는 "디스크를 전부 훑은 뒤 부트섹터를 찍는" 모양이 되고, 그것이
부트킷의 순서라 Windows Defender가 막습니다. 서명이 없어서 더 그렇습니다.

둘을 동시에 만족시키는 순서를 아직 찾지 못했습니다. 그래서 기본값은 백신에
걸리지 않는 쪽으로 두고, 판단은 켜는 사람에게 맡깁니다. 자세한 내용은
[`docs/DEFENDER_FALSE_POSITIVE.md`](docs/DEFENDER_FALSE_POSITIVE.md)에 있습니다.

## 안전

되돌릴 수 없는 작업이라 안전 규칙을 기능이 아니라 명세로 다룹니다.

- **USB 버스에 연결된 장치만** 목록에 나옵니다 (`BusType == 7`). `Removable`
  플래그는 쓰지 않습니다 — USB SSD는 removable=false로, 빈 카드리더는 true로
  보고해서 근거가 되지 못합니다
- 디스크 번호 0은 무조건 거부합니다
- 시스템 드라이브·윈도우 폴더·실행 파일·페이지파일이 있는 디스크는 커널에 직접
  물어 구한 보호 집합으로 차단합니다. WMI 정보가 틀려도 이 방어선은 남습니다
- 디스크 번호는 안정적이지 않으므로, 쓰기 직전 열린 핸들에서 장치 신원을
  다시 확인합니다
- 용량이 모자라거나 쓰기 금지된 USB는 **숨기지 않고** 사유와 함께 선택 불가로
  보여줍니다. 조용히 사라지면 사용자는 인식 실패로 읽습니다

디스크 0 거부, 보호 집합 차단, 신원 재확인은 순수 함수로 구현돼 실제 하드웨어
없이 시험됩니다. 버스 타입 판정만 Windows 호출 결과에 달려 있어 실물 확인이
필요합니다.

## USB 복제

이미 로더를 구워 둔 USB를 다른 USB로 복사합니다. 로더를 다시 받지 않고, 부팅이
확인된 USB를 그대로 하나 더 만들 때 씁니다.

**파티션이 끝나는 지점까지만 복사합니다.** 32GB USB에 5GB 로더가 들어 있으면 5GB만
읽고 씁니다. 전체를 통째로 옮기면 대부분 빈 공간을 복사하느라 13분이 걸립니다.
덤으로 대상 USB가 원본보다 작아도 내용만 들어가면 됩니다.

원본은 읽기 전용으로만 엽니다. 대상 목록에는 원본이 나오지 않습니다.

GPT로 된 USB는 복제하지 않습니다. GPT는 백업 헤더가 디스크 맨 끝에 있어서 크기가
다른 USB로 옮기면 헤더 위치와 CRC를 전부 다시 계산해야 하고, 조용히 틀리면 부팅은
되는데 나중에 깨지는 종류의 문제가 됩니다. m-shell과 RR 로더는 MBR이라 실제로
막힐 일은 없습니다.

## 아직 확인되지 않은 것

만든 사람의 환경(Windows 11 25H2 + SanDisk USB 두 개)에서는 정상 동작을
확인했습니다. 그 밖의 조합은 아직입니다. CI는 가상 디스크(VHD) 두 개를 붙여
쓰기와 복제 경로를 매번 시험하지만, 러너에는 USB가 없습니다.

그래서 **버스 타입 판정, 안전 제거, 실제 부팅**은 원리적으로 자동 검증이 되지
않습니다. 사람이 실물 PC에서 확인해야 하는 항목은
[`docs/MANUAL_TEST.md`](docs/MANUAL_TEST.md)에 모아 두었습니다.

문제를 겪으시면 Windows 버전(`winver`), USB 제조사·모델·용량, 멈춘 단계, 화면에
뜬 오류 문구를 함께 이슈로 남겨 주세요.

## 개발

### 요구사항

- Rust (stable)
- Node.js 20.19+ 또는 22.12+ (Vite 8 요구 사항. CI 는 24 LTS 를 쓴다)
- 리눅스에서 개발하려면 `libwebkit2gtk-4.1-dev` 등 Tauri 의존성

### 명령

```bash
npm install

# CI 가 하는 검사를 그대로 돌린다. 푸시 전에 이것을 실행할 것.
./check.sh

# 개발 실행 (Windows 가 아니면 가짜 장치로 뜬다)
npm run tauri dev
```

윈도우 배포물은 CI(windows-latest)에서만 만든다.

`check.sh` 가 `cargo clippy` 만 돌리지 않는 이유가 있다. `#[cfg(windows)]` 로 감싼
코드는 리눅스에서 아예 컴파일되지 않아 검사에서 빠진다. 실제로 그 때문에 로컬이
초록불인 채로 CI 가 세 번 연속 실패했다. 그래서 Windows 타겟도 함께 검사한다:

```bash
rustup target add x86_64-pc-windows-gnu
sudo apt-get install gcc-mingw-w64-x86-64
```

### 구조

```
src/                  프런트엔드 (TypeScript + Vite, 프레임워크 없음)
src-tauri/src/
  core/               플랫폼 무관. 어디서든 테스트된다
    safety.rs           안전 인터록 (순수 함수)
    loader.rs           릴리스 에셋 해석
    layout.rs           MBR 을 읽어 복사할 길이를 구한다
    sink.rs             장치 쓰기 루프. 굽기와 복제가 공유한다
    runner.rs           굽기 흐름
    cloner.rs           복제 흐름
  device/             Windows API 를 부르는 유일한 곳. 트레이트 뒤에 격리
docs/                 설계 문서와 실물 확인 목록
```

Windows 의존 코드를 트레이트 뒤에 두는 이유는 검증 때문이다. 가짜 구현으로 바꾸면
실제 USB 없이도 안전 규칙과 전체 파이프라인을 시험할 수 있고, 리눅스에서 앱을 띄워
UI 를 확인할 수 있다.

### 테스트가 닿지 않는 곳

`device/windows/` 에는 자동 테스트가 없다. `#[cfg(windows)]` 뒤에 있어 리눅스에서는
컴파일조차 되지 않고, 그 안은 Win32 호출과 결과를 옮기는 배선이라 실제 장치 없이
부를 수 없다. 판정은 `device/prep.rs` 로 빼놓아 그쪽은 잡힌다. Windows 타겟 clippy
는 컴파일과 린트를 볼 뿐 동작을 보지 않는다.

그래서 이 층에서 사용자에게 나가는 문구는 `docs/MANUAL_TEST.md` 의 항목으로만
확인된다. 프런트엔드도 마찬가지로 `tsc` 의 타입 검사가 전부다.
